### 关键发现 1：网页版存在一个「僵尸开关」

`src/components/NotificationSettingsModal.tsx`：

- 第 16-17 行：`vibrateEnabled`，持久化 key 为 `localStorage['app_vibrate_enabled']`
- 第 132 行文案写的是「支持设备点按打卡提供物理触觉反馈」
- 但全仓库 `src/` 里 **唯一** 一处 `navigator.vibrate` 调用在第 51-52 行，
  只在**打开这个开关的瞬间试振 30ms**，业务动作（打卡/计数）里**一处都没接**。

结论：UI 已经承诺了「点按打卡有触觉反馈」，功能却从没落地过。本次实现等于把这个空转开关接上。
→ 复用 `app_vibrate_enabled` 作为总开关即可，不需要新增 key（语义本来就该是 UI 触觉）。
→ 该开关**不代表通知振动**；通知那套是 `NotificationHelper.kt:46 enableVibration(true)` 走通知渠道，
   两者是不同机制，别合并。

### 关键发现 2：安卓侧权限已就位，但零触觉代码

- `AndroidManifest.xml` 第 13 行**已有** `<uses-permission android:name="android.permission.VIBRATE" />`，
  VIBRATE 属普通权限，无需运行时申请 → 安卓侧不用改清单。
- 全 kt 源码搜 `vibrate|Haptic` 只命中 `NotificationHelper` 的 `enableVibration`（通知渠道振动），
  UI 层完全没有任何触觉调用。
- ⚠️ `HabitViewModel` 是**普通 ViewModel**（不是 AndroidViewModel，构造函数只吃 `HabitRepository`，无 Context）。
  所以振动**不要塞进 ViewModel 的业务方法**（toggleCheckIn / stepCounter 等），
  否则要改构造函数 + Factory，污染分层。
  正确落点：Compose UI 层。`LocalHapticFeedback` 最省事（无需权限、跟随系统触觉设置），
  若要自定义时长/波形再用持有 applicationContext 的 Haptics 单例（minSdk 29 可走
  `VibrationEffect.createPredefined` / `createWaveform`）。

## 触觉反馈（振动）功能 —— 已实现，编译验证通过

### 新增 `util/Haptics.kt`（全局触觉引擎，object 单例）

- 三档 `Level.LIGHT / MEDIUM / STRONG`：
  - LIGHT = `createOneShot(12ms, amp 70)`
  - MEDIUM = `createOneShot(22ms, amp 150)`
  - STRONG = 两段波形 `createWaveform(0,18,55,32 / 0,170,0,255)`。
    完成感来自「间隔 + 加重」的**节奏**，单纯延长时长在手感上更像卡顿。
- **70ms 同档节流**，且**分档独立计时**——这点很关键：共用一个时间戳的话，
  连点 LIGHT 会把紧接着的达标 STRONG 一起吞掉。
- 三重准入：设备有马达 + App 开关 + 系统「触觉反馈」总开关。
- 设备不支持振幅控制时**不能**传 amplitudes 数组（0 表示停振，会被静音），
  必须降级用只给 timings 的 `createWaveform(timings, repeat)` 重载。
- `attach()` 在 `HabitApplication.onCreate()` 调用；未 attach 时全部安全 no-op。
- API 31+ 走 VibratorManager，29/30 走 Vibrator；33+ 带 `VibrationAttributes.USAGE_TOUCH`。
- 两个「为什么」：
  - 不用 Compose `LocalHapticFeedback` —— BOM 2024.11.00 只有 LongPress/TextHandleMove 两种，
    表达不出分级。
  - 做成 object 而不是 Composable 参数 —— `CheckInActionReceiver` 在后台也要振，那里没有 Compose 上下文。

## UI 三连 bug 修复（用户实测反馈）

### bug1 完成打卡时卡片四周出现「一圈透明黑框」

根因**不在描边**，在**底色**：`HabitCard.kt` 完成态容器色写成
`DONE_GREEN.copy(alpha = 0.05f)`，是个**半透明**色。而 Material3 的 `Surface`
（Card 底层）实现是：

```
graphicsLayer(shadowElevation, shape, clip = false) → border → background → clip
```

`clip = false` + 半透明背景 = 阴影从背景里**透出来**，沿四边糊出一圈发暗的框。
1dp 的 elevation 阴影很淡，所以观感正是「透明黑框」。

修法：`DONE_GREEN.copy(alpha = 0.05f).compositeOver(colorScheme.surface)`
→ 合成成**不透明**色，观感与网页版 `bg-emerald-500/5` 一致，且阴影不再漏出。
（网页版用半透明底没这问题，因为 CSS 的 box-shadow 不走这套。）

顺带把描边从 `CardDefaults.outlinedCardBorder().copy(brush = ...)` 换成显式
`BorderStroke(1.dp, DONE_GREEN.copy(alpha = 0.3f))`。原写法能用（`BorderStroke`
确实有 `copy(width, brush)`，已 javap 验过），但它取的是 `colorScheme.outlineVariant`，
而本主题只覆盖了 `outline` → outlineVariant 落到 M3 默认值，宽度/颜色不受本主题控制。

### bug2 独立计数器 +1 后位置自动上跳一位

`StandaloneCounterDao.getAllCounters()` 是 `ORDER BY updatedAt DESC`，
而 `applyStep()` / `setCount()` **每次都写 updatedAt** → 点一下 +1，这张卡立刻
变成「最新」并跳到列表最前。

修法：改 `ORDER BY id ASC`（创建顺序）。新建追加在末尾，且与网页版 IndexedDB
`getAll()` 天然按主键升序返回一致。
⚠️ 网页版 `db.ts:loadAllCounters` 里是 `sort((a,b) => b.updatedAt - a.updatedAt)`，
**同一个病，一并改成了 `a.id - b.id`**。这次两份实现都动了。

### bug3 日历格选中绿框时，状态点贴到框边

`CalendarMonthView.kt` 的日期数字只写了 `fontSize = 12.sp`，
但 M3 的 `MaterialTheme` 会把 `LocalTextStyle` 设成 **bodyLarge**，
而 `Text` 的 `fontSize` 参数只覆盖字号，**lineHeight 仍是 bodyLarge 的 24sp**
（`ui/theme/Type.kt` 里就是这么定义的）→ 单行数字的文字块高 24dp，
把下面的状态点一路顶到底。cell 内容区约 40dp，去掉 24dp 文字后点几乎贴着描边。

修法：显式 `lineHeight = 12.sp`（等价网页版的 `leading-none`）。
↑ **这个坑是通用的**：全工程任何 `Text(fontSize = ...)` 裸写都会继承 24sp 行高，
以后写小字号文字要么给 `style = MaterialTheme.typography.xxx`，要么显式指定 lineHeight。

换机器/删 keystore 重建 → 指纹变化 → 朋友必须卸载重装、数据全丢**。

### ③ applicationId 改名：实测**零源码改动**

把 `applicationId` 从 `com.example.habittracker` 改成一个完全不同的值做真实构建：
- `compileDebugKotlin` / `kspDebugKotlin` / `dexBuilderDebug` 全部 **UP-TO-DATE** → 源码与 R 类零变化
- aapt 结果：`package: name='cn.weijing.habit'`，但 `launchable-activity` 仍是
  `com.example.habittracker.MainActivity`

原因：`namespace`（= Java 包名 = 源码目录结构）与 `applicationId`（= 安装身份）是**两个独立概念**。
AGP 用 `namespace` 解析 manifest 里的相对类名（`.MainActivity` → `com.example.habittracker.MainActivity`），
用 `applicationId` 决定安装身份。所以**只改 build.gradle.kts 那一行即可，Java 包名不用动、目录不用搬**。

连带面已逐个排除：
- `AndroidManifest.xml` **没有任何 `<provider>`/authorities**（无 FileProvider）
- `CheckInActionReceiver` **无 intent-filter 且 exported=false** → 靠显式 Intent 唤起，
  `NotificationHelper.ACTION_CHECK_IN = "com.example.habittracker.ACTION_CHECK_IN"` 只是个内部标签，
  **不依赖包名**，改 applicationId 不会失效（但留着旧包名字符串不美观）
- `BootReceiver` 的 intent-filter 全是 `android.intent.action.BOOT_COMPLETED` 等框架 action，与包名无关
- 所有取包名的地方都是**动态**的 `context.packageName`（AddEditHabitDialog:643/992/996、
  SettingsScreen:531/535/556/559），零处硬编码、零处 `BuildConfig.APPLICATION_ID`、零处 `getIdentifier()`
- `backup_rules.xml` / `data_extraction_rules.xml` 用相对 domain（`database`/`file`），自动跟随

→ 唯一真正的代价是**社会性**的：改完对已安装的人就是另一个 App，原数据不跟过去。

## 版本号升到 1.0（用户指令：「版本改成1.0」）

### ⚠️ 顺手拔掉一个 versionCode 的坑

旧写法是 `versionCode` 与 `versionName` 末段对齐（`0.0.8` → `8`），注释还写着「发版时一起加」。

|---|---|
| 1.0（= 1.0.0） | 10000 |
| 1.0.1 | 10001 |
| 1.1 | 10100 |
| 2.0 | 20000 |

从 8 直接跳到 10000 完全没问题，Android 只要求单调递增，不要求连续。
`build.gradle.kts` 里的注释也一并改写，并补了一句「只改 name 不改 code = 等于没发新版」。

## 🔥 事故与修复：全部自绘图标渲染成空白（用户实测「图标全没了」）

用户装了 1.0 release 后反馈：**应用内所有图标都不见了**，要求回滚到 material-icons-extended（接受 59MB）。
没有直接回滚 —— 先定位，结果是一个**一行就能修的库 API 误解**，体积优势（20.9MB）得以保住。

### 根因（钉在字节码层面）

`HabitIcons.kt` 的 `icon()` 里原来写的是：

```kotlin
path(fill = SolidColor(Color.Black), pathFillType = ...) {
    addPathNodes(d)          // ❌ 合法、无警告、但完全无效
}
```

反编译自己的 class 直接看到真相：

```
invokestatic VectorKt.addPathNodes:(Ljava/lang/String;)Ljava/util/List;
pop                                                    ← 返回值被丢弃
```

**库里的 `addPathNodes` 是普通函数 `(String) -> List<PathNode>`，不是 `PathBuilder` 的扩展。**
写在尾随 lambda 里当语句时，它算出一个 List 然后扔掉 —— path 里 **0 个节点**，
于是 35 个自绘图标全部渲染成空白。而 `PathBuilder` 只有 `moveTo/lineTo` 这类基本指令
（javap 确认：**没有**任何接收节点列表的方法），公开的 `path {}` 扩展连 `pathFillType` 都不收。

**唯一入口是 `ImageVector.Builder.addPath(pathData = ...)`**（成员函数，非扩展；javap 可见其
第一个参数就是 `List<PathNode>`）。改成 `addPath(pathData = addPathNodes(d), fill = ..., pathFillType = ...)`
即修复，字节码里从 `pop` 变成 `astore`。

### 为什么上一轮的验证全都没抓住

上一轮我验的是：①编译成功 ②d 串与源 SVG 逐字节一致 ③两端 key 表对齐。
**三条都没碰到真正的渲染路径** —— 这个 bug 的特点就是「编译零警告、单测不报错、APK 正常」。
当时我还写明了「图标外观的肉眼确认没做」，只推了个 HTML 对照表给用户 —— 而那个 HTML 渲染的是
**原始 SVG**，跟 Kotlin 侧能不能画出来毫无关系。这就是漏网的完整链条。

### 新增 `HabitIconsTest`（4 条，真功能验证）

关键发现：`ImageVector.getRoot()` / `VectorGroup` / `VectorPath.getPathData()` **全是 public**，
所以 JVM 单测里能直接数节点，不需要真机：

- `自绘图标必须带路径节点` —— 反射遍历 `UiIcons`(19) + `HabitIcons`(16)，逐个断言节点数 > 0
  （用 `holder.javaClass.methods` 过滤，避免手抄清单漏项；另加 `all.size >= 30` 防止反射失效导致「假绿」）
- `getIconVector 的所有 key 都解析成非空矢量图` + 未知 key 回退到非空 Star
- `PRESET_ICONS 的 key 与 getIconVector 一一对应`
- **`探针：把 addPathNodes 写在尾随 lambda 里会静默产出空路径`** —— 刻意复现错误写法并断言其节点数为 0。
  这条是**反向证据**：证明了上面几条不是空转；若哪天 Compose 改了行为它会先炸，提醒更新注释。

### 验证（全部实测）

| 项 | 结果 |
|---|---|
| 单测 | **16 passed / 0 failed**（12 旧 + 4 新） |
| release 字节码 | `addPathNodes` → `astore 14`（真用上了，不再是 `pop`） |
| APK | `versionCode=10000 versionName=1.0`，签名 SHA-256 `1bb71eeb…`（**与坏版本同签名 → 可直接覆盖升级**） |
| 体积 | **21,915,379 B ≈ 20.90 MB**（没回到 59MB） |
| 启动图标 | 未受影响（走 `mipmap-*/ic_launcher_foreground.png`，文件都在） |

### 教训（已写进代码注释与 MEMORY.md）

1. **「编译通过」+「数据逐字节正确」都不等于「功能正确」** —— 必须打在那条真实的执行路径上。
2. 自己的代码出现「静默无效果」时，`javap -c` 反编译自己的 class 是最快的定位手段，
   比反复读源码猜快得多（`pop` vs `astore` 一眼定案）。
3. 找 Compose 的 API 时，**javap 直接列 jar 里的真实签名**胜过回忆文档 ——
   这次连续两轮都靠它纠正了错误假设（先否掉 `path(pathData=)`，再确认 `addPath`）。

## 1.0.1：独立计数器「周期自动归零」+ 图标一起发版（14:42~15:05）

需求原话：「独立计数器创建的时候，增加一个设置，是否选择每日、每周、每月或者每N天归零。
每日喝水，我今天喝三杯，第二天归零，但昨天喝的记录要保存。」

### 设计决定

| 取舍 | 选择 | 理由 |
|---|---|---|
| 归零时机 | **惰性结算**（前台恢复时算） | 本 App 无 INTERNET、省电优先；WorkManager/AlarmManager 在国产 ROM 被延迟是常态，漏跑一次用户就看到「过了零点没归零」。惰性结算把正确性绑在「用户正看着屏幕」那一刻，触发即必然正确 |
| 历史载体 | 新表 `counter_period_logs` | 清零前把上周期值抄一份再清计数，不动 `currentCount` 的既有语义（库存类计数器如「冰箱可乐」仍可不归零） |
| 周/月起点 | **自然周（周一）/自然月**，而非从创建日滚动 | 「每周归零」的直觉是自然周；只有「每 N 天」没有自然边界，才用锚点滚动 |
| 同周期多次归档 | **合并累加**，不新增记录 | 否则「上午喝 3 杯手动清零、下午又喝 2 杯」会在历史里变成 9/20 的 3 杯 + 9/20 的 2 杯两行，看着像 bug |
| 空周期 | 不留记录 | 跨很多天才打开 App 时，历史里堆一串 0 毫无信息量 |

### 改动清单

- `data/entity/StandaloneCounter.kt`：加 `resetPeriod`/`resetIntervalDays`/`periodStartDate`
  （锚点语义是「当前周期从哪天开始」，不是「上次归零发生在哪天」）+ `RESET_*` 常量与 `RESET_OPTIONS`。
- `data/entity/CounterPeriodLog.kt`（新）：FK CASCADE 到计数器，单位做快照冗余（用户改单位后老记录不该跟着变）。
- `data/HabitDatabase.kt`：**version 3 → 4** + `MIGRATION_3_4`（三列 + 建表 + 索引）。
  ⚠️ NOT NULL 新列**必须带 DEFAULT**；实体侧不写 `@ColumnInfo(defaultValue)` 时 Room 不校验该列 default，
  所以「DDL 带 DEFAULT、实体不带」是既安全又必要的组合。

### 四个真坑（结论性）

1. **Room 在鸿蒙路线里没有对应物**。KMP 上的答案是 SQLDelight，但其官方 driver 也无 OHOS；
   CPF 生态有 `SQLiter` 在补。真实案例（AIVoice 三端改造）里 Room 被移到 `roomMain` 只给 Android，
   鸿蒙端直接「无持久化」。本项目整个 App 就活在那几张表上 → 数据层必须重写，是最大工作量。
2. **提醒功能要走「代理提醒 reminderAgentManager」且需邮件申请**（hwpush@huawei.com，10 个工作日）。

   坏消息：手机/平板/PC 有管控；单应用上限 30 个有效提醒；**通知栏按钮无法直接写库**
   （Android 的 `CheckInActionReceiver` 那套交互得重设计）。`BootReceiver` 重启建闹钟反而可省
   （鸿蒙系统代理，进程死了也提醒）。
3. **版本要集体搬家**：`Kotlin 2.0.21 → 2.2.21`、**`AGP 8.7.3 → 8.6.0`（要降级！）**、

   Coil 需 ohos 变体。KSP 也需跟着 Kotlin 版本走。
4. **UI 里的 AndroidX 味要摘干净**：`dynamicLightColorScheme`/`dynamicDarkColorScheme`（Material You
